# v2.0.8 Release Notes

> Release date: 2026-09-04
> Tag: `v2.0.8`
> Source of truth: [docs/VERSION_MANAGEMENT.md](../docs/VERSION_MANAGEMENT.md)
> Retro: [docs/INCIDENT_REPORT_v2.0.7.md](../docs/INCIDENT_REPORT_v2.0.7.md)

This is a **tooling / process release**. v2.0.7 was the first release to be published
end-to-end through the unified `release_cli.py`, but the tooling was a hacky shell
script that lived only on the developer's machine. v2.0.8 turns those scripts into
a documented SOP + a cross-platform CLI, and closes 6 of the 7 incidents from the
v2.0.7 retro.

No source-code API changes. No model/provider changes. Pure documentation,
process, and tooling.

## What's in v2.0.8

### Unified release CLI — `scripts/release/release_cli.py`

Replaces the v2.0.7 ad-hoc bash scripts with a single 100% stdlib Python CLI that
works on Windows / Linux / macOS. Six subcommands:

| subcommand | purpose |
|---|---|
| `github` | Push tag + create GitHub Release (gh CLI or REST API fallback) |
| `gitee` | Push to Gitee mirror + optionally create Gitee Release |
| `protect` | Apply branch protection rules (delegates to `.sh`/`.ps1`) |
| `cleanup` | Orphan-branch cleanup per §7.6 |
| `webhook` | Apply side-effects on PR merge events |
| `status` | Show latest release + tag/protection state |

Designed for both interactive use and CI consumption. No third-party deps
(urllib only). Tested on PowerShell 5.1 / Bash 4+.

### Branch-protection one-click — `scripts/release/apply_branch_protection.{sh,ps1}`

Applies the master / release/* protection payload documented in §7.5 of
`VERSION_MANAGEMENT.md`. The script enforces that the payload includes the
`required_status_checks` and `restrictions` fields (even as `null`), which is
the cause of I-2 in the incident report.

### Release SOP — `docs/VERSION_MANAGEMENT.md` (~610 lines)

The "source of truth" for version management. Eight sections + two appendices:

1. Version numbering (SemVer + suffix conventions)
2. CHANGELOG maintenance
3. Local tag workflow
4. Push to GitHub
5. Create GitHub Release
6. Gitee mirror sync
7. **Post-release cleanup** (the meat — see §7.6 for the orphan-branch SOP)
8. FAQ

Appendix A: common-commands cheat sheet. Appendix B: document history.

### Incident retro — `docs/INCIDENT_REPORT_v2.0.7.md`

Six post-mortems from the v2.0.7 release with action items. Drives §7.5/§7.6 of
the SOP. New action items A-5 / A-6 / A-7 are tracked here.

### Release PR template — `.github/PULL_REQUEST_TEMPLATE/release.md`

Markdown checklist mirroring §7.6.4 — the "post-release self-check" that
publishes the v2.0.7 cleanup work.

### `.gitattributes` — line-ending policy

Forces `.sh` LF / `.ps1` CRLF so PowerShell scripts don't get clobbered by the
LF-only Linux convention (or vice-versa).

## Known Caveats

- **PAT workflow scope missing**: Workflow files (`.github/workflows/*.yml`) are
  written locally but not pushed because the current PAT lacks the `workflow`
  scope. The release CLI is fully usable without workflows — `release.yml` and
  `pr-merge-label.yml` are optional accelerators.
  See INCIDENT_REPORT I-7 for permanent fix.
  > **Status update (v2.0.9)**: the two workflow files are now committed to
  > `master`; they will start running automatically as soon as a PAT with the
  > `workflow` scope is configured. See [release_notes/v2.0.9.md](./v2.0.9.md).
- **No status checks**: master branch protection does not require CI status
  checks yet because the project has no CI workflows.
- **Single-owner payload**: master uses `required_approving_review_count=0`
  to avoid the self-merge deadlock. When a second maintainer joins, switch
  to `=1` via `release_cli.py protect master --enforce-admins` + the
  multi-owner payload template in §7.5.2.

## Migration

No breaking change. After tagging `v2.0.8`:

```bash
git fetch origin && git checkout master && git pull
```

No data migration, no config change. The release CLI is opt-in — old workflows
(manual gh CLI / curl) still work.
